# Experiments

> Optional module. Keep it if the project tests a new way of working (an AI-assisted workflow, a new tool, a new method) and you want that learning to outlast the project.

A weekly summary says *what happened*. An experiment entry says *how to do it again*. The summary is disposable within a month; the entry is the thing you still want two projects later.

**To add one:** ask Claude to run the `experiment-capture` skill (about 10–15 minutes, conversational), or copy `_templates/experiment.md` to `experiments/YYYY-MM-DD_short-name.md` and fill it in, leaving unknowns as `TBD`.

## Conventions

- **Date = when it was run**, not when it was written up.
- **Status is mandatory** and kept current: `experimental` / `works` / `production-ready` / `parked` / `failed`.
- **The losses section is never empty.** Memory inflates wins, and a tracker full of successes is one nobody trusts.
- **Prompts verbatim.** This is the most reproducibility-critical part.
- **Log failures.** An honest failure saves the next person more time than a success.
- **Measure from the start:** a baseline ("compared to what?") and cost. Many metered tools only show a rolling window, so check at kickoff.
